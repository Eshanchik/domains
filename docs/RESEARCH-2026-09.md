# DomainGuard — полный ресерч продукта и план развития (сентябрь 2026)

_Срез на 2026-09-21. Кодовая база: main @ T63 (изменений с 24.08 не было). Метод: 9 независимых ревизий кода по направлениям + синтез + срез прода (только чтение). Каждая находка привязана к файлу/поведению._

> Итог одной строкой: **фундамент сделан правильно, но как ежедневный продукт DomainGuard сейчас «слепой и тихий» — ⅓ парка мёртвая, 85% алертов никому не доставляются, UI почти не открывают.** Дорожная карта — 33 задачи (T64–T96) в четырёх фазах; детальные задачи — в `docs/PLAN.md`.


## 1. Резюме

DomainGuard за 63 задачи стал реальным реестром ~1000 доменов трёх компаний с проверками RDAP/WHOIS/SSL/VT/DNS/health-check, per-user скоупами, MCP-сервером и rich-дайджестом в Discord — фундамент (сервисный слой, provenance полей, лимитеры и circuit breaker, Fernet, инъекция времени в тестах) сделан правильно, и именно поэтому большинство P0 ниже — задачи размера S/M, а не переписывание. Но как ежедневный внутренний продукт он пока «слепой и тихий»: девять независимых ревизий сошлись на одних и тех же системных дырах, и почти все они объясняют уже пережитые инциденты (потеря egress после переезда, «замолчавший» бэклог после T63, шторм ns_change, запертый админ, crash-loop mcp-контейнера). Конкретно: архивные домены продолжают проверяться и заново рождают HIGH-алерты; любое сохранение формы домена навсегда замораживает expiry_date как manual (сравнение aware/naive datetime); instant-алерт помечается доставленным до отправки и при сбое канала теряется навсегда; проверки, упёршиеся в rate-limit, выбрасываются на 1–7 дней; за самим DomainGuard никто не следит («net ok» в шапке захардкожен, heartbeat/метрик очереди/канарейки egress нет); курсы валют сломаны и платежи не в USD молча не сохраняются; доступ восстанавливается только SQL-ом; документация описывает несуществующий прод (DigitalOcean/deploy.sh). Для персон «менеджер» и «финансист» рабочих экранов практически нет (нет страницы компании, /costs — 30-дневный список без итога и без цен для GoDaddy/ручных регистраторов), а для ops главная страница /alerts не поддерживает ни один сценарий триажа (нет ack/snooze/массовых действий/истории/пагинации). Roadmap из 33 задач (после корректировки приоритетов по прод-данным) в четырёх фазах: (1) 10 задач гигиены — после них «тихо» будет означать «всё хорошо», а не «сломалось»; (2) 10 задач ежедневного удобства — workflow алертов, жизненный цикл просроченных, карточка/список v2, профиль и 2FA; (3) 4 задачи финансов — цены для всех регистраторов, прогноз по кварталам и компаниям с экспортом, платежи v2 с mark_renewed, сверка; (4) 8 задач платформы — доступ и аудит, MCP-помощник оператора, воспроизводимая сборка и честные тесты, REST/вебхуки, правила алертов, коннекторы, данные на масштабе. Ориентировочно в текущем темпе одного разработчика с Claude Code: фаза 1 — 3–4 недели, фаза 2 — 6–8, фаза 3 — 3, фаза 4 — 6–8 недель; 14 задач помечены L и при нумерации их разумно резать на два PR (миграция+сервис / UI). Отдельно стоит зафиксировать в SPEC §11 два продуктовых решения, которые roadmap принимает по умолчанию: напоминания об открытых crit-алертах в каждом дайджесте (а не эскалация, FR-AL-6 не делаем) и авто-архив просроченных по правилу с grace-периодом вместо CLI.

**Корректировки по прод-данным** (см. §3): жизненный цикл домена поднят в P0 (38% парка не резолвится — это корень шума и трёх ручных чисток); покрытие каналами выделено в отдельный P0 (104 из 122 активных алертов не доставлены никому); курсы валют перенесены из P0 в фазу финансов (платежей в системе 0, это не блокирует ежедневную работу). Тезис «новый канал GT1 получит «нечего отправлять»» устарел: после пересброса 24.08 события GT1 не помечены и уйдут в первой же сводке нового канала.


## 2. Что уже работает хорошо

Ядро реестра здоровое: нормализованный FQDN (IDN/punycode через UTS-46), per-field provenance `field_sources` с правилом «manual не перетирается» во всех трёх писателях, линейная цепочка из 17 Alembic-ревизий с одной головой, партиционированный `check_result` с retention, история ключевых полей и аудит на всех мутациях, пагинированные списки с индексами и `ssl_status_map` без N+1 (NFR-2 при 10k доменов выполняется). Слой проверок архитектурно правильный: атомарный токен-бакет и дневной бюджет на Lua в Redis, circuit breaker с half-open и экспортом в /metrics, retry с джиттером, RDAP→WHOIS fallback со stale-семантикой без затирания данных, два SSL-handshake (даты видны даже при сломанной цепочке), SSRF-guard на каждом hop редиректа health-check'а, фикс NS-baseline (T62). Алертинг после T50–T63 аккуратен по формату: дедуп через partial unique index на dedupe_key, rich-дайджест с нативными Discord embeds/Telegram HTML и chunking под лимиты каналов, маршрутизация project→company→global, deliver-once, идемпотентность дайджеста по дню. Безопасность на фундаменте крепкая: argon2id с rehash, серверные отзываемые сессии в Redis, lockout + nginx rate-limit на /login и /mcp, скоупы последовательно во всех трёх слоях (web/API/MCP, write-side дыры закрыты в T52), секреты в Fernet at-rest и никогда в аудит-diff, Google OAuth только для существующих пользователей, MCP OAuth 2.1 с PKCE/DCR/consent и ротацией refresh; 21 MCP-инструмент — тонкие обёртки над теми же сервисами, поэтому скоуп и аудит применяются автоматически. UI стилистически целостен (BTOP-скин, единый макрос `ui.panel` во всех 29 шаблонах — дизайн меняется в одном месте), импорт с dry-run предпросмотром diff, фильтры сохраняются при сортировке/пагинации, чипы проектов, экспорт CSV по фильтру, карточка домена стала посадочной страницей из дайджеста, пустые состояния осмысленные. Инфраструктура в ops-adera сделана лучше, чем следует из документации приложения: ночной pg_dump + restic в S3 с еженедельным `restic check` и алертом «бэкап старше 26 ч», egress воркера закодирован в compose, Loki/Grafana/Prometheus с дашбордом по dg_*-метрикам, гейт миграции перед стартом, откат по digest; 323 теста на реальных Postgres+Redis в CI со сценариями 429/5xx/timeout для RDAP/VT/SSL/Telegram/webhook, и каждая недавняя задача (T60–T63) приходила с тестами.

## 4. Топ-рисков (от самого опасного)

0. **Мёртвый парк маскирует живые проблемы.** 128 из 333 активных доменов неделю не резолвятся (~33 не зарегистрированы, ~70 без DNS-записей); они дают 49% SSL-«ошибок», 21% DNS-stale, часть expiry-алертов и три ручные чистки (T47, T55, 24.08). У домена нет жизненного цикла кроме `is_active`, синк не замечает исчезнувшие из аккаунта домены. _(прод-срез)_
1. Тихая остановка мониторинга: нет heartbeat планировщика, метрик очереди/просрочки/устаревания, канарейки egress и внешнего dead-man; healthcheck воркера = redis.ping(), в Grafana ни одного правила на dg_* — зависший планировщик или воркер без сети обнаруживаются постфактум по шторму или по тишине (уже случилось после переезда). Для системы, чья единственная задача — вовремя предупредить, это равно потере домена.
2. Потеря критичных алертов при ложной уверенности «раз тихо — всё ок»: `notified_at` ставится при постановке в очередь, сбой канала глотается без исключения (at-most-once, окно ретраев ~1.5 с), в дайджест такое событие уже не попадёт; GT1/Antares без каналов копят алерты молча (104 из 122 активных алертов сейчас не доставлены никому); после пересброса 24.08 их события не помечены и уйдут в первой сводке нового канала — но пока канала нет, любая критичная проблема GT1 остаётся невидимой.
3. Тихая порча основной метрики продукта: каждое сохранение формы «Изменить домен» (даже ради тега) помечает expiry_date как manual и навсегда отключает обновление из RDAP/регистратора; параллельно RDAP и API перетирают друг друга по дате до 5 раз в день. Источники полей нигде не показываются, поэтому расхождение с реальностью по всем редактировавшимся доменам накапливается незаметно и даёт ложные/пропущенные expiry-алерты.
4. Архивные и просроченные домены не выведены из жизненного цикла: расписания проверок не удаляются, `enqueue_due`/`evaluate_*`/`dispatch_instant` не смотрят is_active — после архивации следующая RDAP-проверка снова шлёт HIGH «истекает через −1638 дн.», VT-бюджет (500/день) и RDAP-квоты жгутся на кладбище, авто-архива нет (только dry-run CLI для GoDaddy), просроченные замусоривают счётчики и прогноз.
5. Проверки молча пропускаются: при rate_limited/budget_exhausted/circuit_open проверка не переставляется, а `next_check_at` уже сдвинут на весь интервал — после любого бэклога (backfill, простой, восстановление egress) большинство VT-проверок выпадает на 7 дней, RDAP/SSL — на сутки; исключения вне RdapError (падение IANA bootstrap, не-JSON) роняют актор без записи stale; сообщения уходят в checks.DQ, которую никто не читает.
6. Единая точка отказа доступа и секретов: один админ без пути восстановления пароля (`ensure_admin` не меняет пароль, `make create-admin` бесполезен), 2FA без recovery-кодов и сброса, самодеактивация не запрещена; потеря/смена DG_MASTER_KEY даёт «здоровый» /readyz при молча мёртвых VT/Telegram/регистраторах/2FA, ротации ключа нет, `.deploy-secrets` не в .gitignore; флаг «Разрешён MCP» обходится любым dg_-токеном.
7. Недостоверные финансы и невоспроизводимая сборка: exchangerate.host требует ключ → платежи в UAH/EUR молча не сохраняются, прогноз ≤30 дней включает истёкшие и исключает домены без цены (все GoDaddy/ручные); без lock-файла и smoke-импорта entrypoint-ов контейнер падает при зелёном CI (уже было с mcp 2.0), деплой без sha-тегов и дампа перед миграцией, локально 73% тестов тихо скипаются, документация описывает несуществующий прод.


## 5. Находки по направлениям

_Severity — влияние на ежедневное использование/безопасность; effort — S (<1 дн.), M (1–3 дн.), L (>3 дн.). Полные обоснования и скоуп — в задачах PLAN.md._


### MCP-сервер и REST API

MCP-сервер архитектурно сделан правильно (тонкие обёртки над теми же сервисами, что и UI → scope и аудит «бесплатно», OAuth 2.1 для claude.ai + dg_-токены для скриптов, 21 инструмент, тесты на скоуп). Но как ежедневный продукт для ассистента он пока «CRUD-набор», а не «помощник оператора»: нет инструмента «что требует внимания», list_alerts без пагинации/фильтров (при шторме ns_change ответ переполняет контекст), продление домена через MCP — двухшаговая ловушка (update_domain навсегда блокирует expiry_date от RDAP), write-инструменты не идемпотентны при ретраях, нет массовых операций/синка регистратора/каналов, которыми люди пользуются из UI каждый день. REST API — заглушка из 3 read-only эндпоинтов без схем и securityScheme в OpenAPI, вопреки SPEC FR-API-1. Есть дыра доступа: флаг mcp_allowed проверяется только на consent-экране — dg_-токен его обходит, а выданные OAuth-гранты не перепроверяются и админу невидимы. Аудит действий ассистента неполный (resolve_alert не аудируется, нет маркера канала ui/api/mcp) и его никто не может прочитать (нет страницы/API/инструмента).

**Сильные стороны:** Единый сервисный слой: каждый MCP-инструмент — `tools.py (session, user, …)` → те же `app/services/*`, что и UI, поэтому scope-фильтрация (T52) и `record_audit…; Безопасные дефолты: `import_domains(dry_run=True)` по умолчанию, `bulk_add_health_check` работает только по доменам в скоупе и возвращает applied/skipped, `upd…; OAuth 2.1 (PKCE + DCR + consent на нашем UI с гейтом `mcp_allowed`) — claude.ai custom connector подключается штатно; параллельно работает Bearer `dg_` для CI/…; Edge-защита: nginx `limit_req` на `/mcp` (300r/m) и `/login`; DNS-rebinding guard осознанно отключён с комментарием почему; секреты не попадают в ответы инстру….

### Алерты и уведомления

Движок алертов после T50–T63 стал аккуратным по формату (rich-дайджест, chunking, группировка, исключение архива, deliver-once), но модель доставки осталась «одно событие = одно сообщение, где-нибудь, когда-нибудь». Из кода видно пять системных дыр: (1) instant-алерт помечается доставленным ещё до реальной отправки (`alerts.py:370-376`), а сбой отправки глотается без исключения (`notifications.py:238-242`) — при потере egress воркером высокоприоритетные алерты теряются навсегда, дайджест их уже не подхватит; (2) deliver-once превратил дайджест в «дельту новых событий»: просроченные домены, ≤1 день, VT-детекты и упавшие health-check'и приходят один раз и замолкают, шапка «Активных алертов: N» и «Отправить сейчас → нечего отправлять» врут; (3) архивные домены продолжают проверяться (`enqueue_due` не смотрит `Domain.is_active`) и после архивации снова рождают instant-алерты «истекает через -1638 дн.», а `archive_expired` никто не вызывает автоматически; (4) компании без канала (GT1/Antares) копят алерты молча и UI об этом не говорит (на проде 104 из 122 активных алертов не доставлены никому; после пересброса 24.08 они не помечены и уйдут в первой сводке нового канала); (5) «Резолв» на expiry/VT/SSL — это отложить до следующей проверки (re-fire на следующий день), ack/snooze/ответственного нет, `Project.responsible_user_id` в алертах не используется. ### Безопасность и доступ

Фундамент безопасности у DomainGuard крепкий: argon2 с rehash, серверные сессии в Redis (отзываемые), lockout + nginx rate-limit на /login, последовательные scope-проверки во всех трёх слоях (web/API/MCP), секреты в Fernet at-rest и никогда в аудит-diff, Google OAuth только для существующих пользователей, MCP OAuth с PKCE/одноразовыми кодами/ротацией refresh. Но «жизненный цикл аккаунта» как продукт отсутствует: нет ни одного способа восстановить пароль (ни self-service, ни CLI — `ensure_admin` не трогает пароль существующего юзера, поэтому админ и оказался запертым), пользователи вообще не могут сменить свой пароль, 2FA без recovery-кодов и без сброса админом, потеря `DG_MASTER_KEY` = вечный lockout всех с 2FA и «тихая» смерть VT/Telegram/регистраторов при здоровом `/readyz` (все `CryptoError` глотаются), аудит-лог пишется, но его никто не может прочитать (нет ни UI, ни API), а флаг «Разрешён MCP» обходится обычным dg_-токеном и не отзывается. Плюс не сделаны отложенные из T39 (pip-audit, DB least-privilege, CSP). Главные приоритеты: break-glass восстановление доступа (P0, 1 день), профиль/смена пароля/сессии, 2FA v2, UI аудита, гигиена мастер-ключа.

### Надёжность, эксплуатация, наблюдаемость

Инфраструктурная часть в ops-adera сделана заметно лучше, чем кажется из репозитория приложения: бэкапы есть (ночной pg_dump + restic в S3 + еженедельная проверка + алерт «бэкап старше 26 ч» + Telegram при падении юнита), egress воркера закодирован в compose, есть Loki/Grafana/Prometheus с дашбордом по приложению, лимиты ресурсов, гейт миграции перед стартом контейнеров. Главная дыра — «кто следит за сторожем»: DomainGuard может тихо перестать проверять домены (планировщик завис, воркер без egress, очередь растёт, проверки упираются в rate-limit) и ни одна метрика/алерт этого не покажет — ровно так прошёл инцидент с DNS после переезда. Вторая группа проблем — тихие потери: проверки, попавшие под rate-limit/circuit-breaker, пропускаются на 1–7 дней; алерты помечаются «доставлено» при постановке в очередь, а не после отправки; архивные домены продолжают проверяться и алертить. Третья — процесс деплоя: мутабельный тег latest, без sha, без дампа перед миграцией, post-deploy smoke = только /healthz, CI не ловит дрейф миграций, локально интеграционные тесты молча скипаются. Плюс документация приложения описывает уже несуществующий прод (DigitalOcean/nginx/certbot/deploy.sh), а сброс пароля админа возможен только через SQL.

### Проверки и внешние интеграции

Слой проверок построен правильно по архитектуре (атомарный токен-бакет и дневной бюджет в Redis на Lua, circuit breaker с half-open, retry с джиттером, RDAP→WHOIS fallback, stale-семантика без затирания данных, SSRF-guard на каждом hop редиректа), но в ежедневной эксплуатации есть три системных дыры. (1) Отказ лимитера/бюджета/брейкера не откладывает проверку, а ВЫБРАСЫВАЕТ её на весь интервал: планировщик двигает next_check_at до диспатча, воркер при "rate_limited" просто логирует — для VT (4/мин, интервал 7 дней, все 1000 доменов созревают одновременно после backfill) это означает, что большая часть VT-проверок не выполняется неделями, и никто этого не видит. (2) Жизненный цикл домена не связан с проверками: архивация не удаляет CheckSchedule/не отключает health-check'и, планировщик не фильтрует is_active, evaluate_after_check тоже — заархивированный истёкший домен на следующий день порождает новое high-событие и уходит в Discord; чистка "мертвецов" — только ручной CLI-скрипт, Namecheap-коннектор игнорирует IsExpired, а домены, исчезнувшие из аккаунта регистратора, никак не помечаются. ### Реестр доменов и модель данных

Реестр доменов построен на здоровом фундаменте: уникальный нормализованный FQDN (IDN/punycode через idna UTS-46), per-field provenance `field_sources` с правилом «manual не перетирается», линейная цепочка из 17 Alembic-ревизий с одной головой, партиционированный `check_result` с retention, история ключевых полей и аудит на все мутации. Но для ежедневной работы с ~1000 доменами трёх компаний есть три критичных дефекта в самой модели данных и её обработке: (1) архивация домена не останавливает мониторинг — `CheckSchedule` не удаляется, `enqueue_due` и все проверки игнорируют `is_active`, и `evaluate_expiry` заново создаёт HIGH-событие `{id}:expiry:1` для архивного просроченного домена на следующий же день после того, как архивация его резолвила; (2) форма редактирования домена при ЛЮБОМ сохранении (даже только заметок) помечает `expiry_date` как `manual` из-за сравнения naive-даты из формы с tz-aware датой из БД — после этого RDAP и синк регистратора навсегда перестают обновлять дату истечения, а в UI нет ни индикатора, ни способа снять блокировку; (3) RDAP и API регистратора перетирают друг друга по `expiry_date` (Namecheap отдаёт только дату → полночь UTC, RDAP — точное время) — значение осциллирует и каждый прогон пишет строку в `domain_field_history`.
